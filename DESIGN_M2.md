# Module 2 — Execution Engine Design

## Architecture and contracts

The executor is a tree of objects implementing `open()`, `next()`, `close()`
and `counters()`. `exec.py run` reads physical-plan JSON and pulls rows from
the root; `exec.py trace` prints each operator's counters. Child operators
are never accessed through a global in-memory relation. Base data is read
through M1 `HeapFile.scan()`; temporary data uses M1 `DiskManager` to read
and write fixed 4,096-byte pages. Each operator owns its temporary files and
removes them when closed.

Supported operators:

- `seqscan`, `filter`, `project`, `limit` (pipelined)
- `sort` (external multi-pass merge)
- `distinct` and `group_by` (`sort` and `hash` modes)
- `nested_loop_join` (disk-staged block nested loop)
- `sort_merge_join` (disk-staged sorted streams, spilling duplicate groups)
- `hash_join` (Grace partitioning with block-join overflow fallback)
- `union_all`, `union`, `intersect`, `except`

Plan validation checks required fields, their basic types, modes, operators,
columns, and condition operand types; invalid conditions are rejected before
opening table scans. Column names are qualified. Join schemas concatenate the
original left then right schema. Projection retains duplicates; distinct is
explicit. A self-join without a rename/alias operator has duplicate qualified
names and is rejected. Nonmatching data types are errors.

## Allocating the B-page budget

One page is 4096 bytes; these allocations refer to page-sized data, not
Python interpreter overhead:

1. `seqscan` uses a 2-frame M1 pool so that the directory and data page can
   both be pinned. A pipelined filter or project keeps only the current row.
2. External run generation reserves two frames for the input M1 heap scan,
   one temporary output page, and `max(1,B-3)` frame-equivalents for encoded
   rows. A merge uses at most B-1 input runs plus one output page; the final
   pass streams from up to B-1 runs without writing a final run.
3. Hash partitioning first stages the child to disk. Its partition phase
   then uses one input page and B-1 output page buffers, without holding
   child heap pages concurrently. Each build partition of at most B-2 pages
   is held in a hash table. Oversized/skewed partitions use bounded
   nested-loop blocks instead.
4. Block nested loop stages each child to disk, then holds B-2 pages of
   outer tuples and one input page for each of the outer and inner readers.
5. Sort-merge joins independently sort and stage each child before merging
   the two streams. Duplicate-key runs on the inner side are spilled to disk
   rather than kept as an unbounded Python list. Every matching pair is
   generated by rewinding that run.
6. Set operators sort/deduplicate and stage each input sequentially so that
   only two readers are active during the final merge.
7. Hash distinct and hash group-by partition on stable key hashes. Fitting
   partitions are processed using an in-memory set or aggregate dictionary;
   oversized partitions fall back to the external sort variant.

**Caveat:** frame allocation is managed structurally rather than by a
central runtime reservation object. The peak concurrent allowance therefore
has no independent run-time monitor. Python container overhead is not
included in the page-equivalent accounting. We do not claim this proves all
possible nested plans satisfy the global B limit, particularly nested
blocking operations under arbitrary JSON plans.

## Disk temporary pages and cleanup

Temporary pages store a 2-byte record count, followed by length-prefixed
records. INT and VARCHAR use the M1 byte encodings; executor-only intermediate
REAL results (such as AVG) are encoded as eight-byte little-endian floats.
This does not extend M1 base-table types. The page reader
owns one page and the writer owns one page. All writes go through M1
`DiskManager.write_page` and all reads through `read_page` so their I/O
counters can be collected. Files are deleted on `close()`.

## Comparisons and I/O counters

`tuples_out` counts root/operator `next()` results, not intermediate rows
allocated in Python. Filter increments once per row examined. Block nested
loop increments once per pair tested and produces exactly |R|×|S|
comparisons. Hash join counts all examined candidate pairs, including skew
fallback. Sort-merge counts key comparisons and matched-pair checks;
Python built-in per-run sort comparisons are not independently instrumented.
Temporary file I/O is attributed to the operator that wrote/read the file;
M1 heap reads are attributed to the underlying seqscan. Counters depend on
the actual staging strategy and are therefore not necessarily equal to
textbook ideal join formulas; see `REPORT_M2.md`.

## Design tradeoffs, tests, and known limitations

The conservative sort run allocation makes more merge passes at B=4 than
an isolated B-frame external sorter would. Staging inputs simplifies buffer
accounting but adds page reads/writes. We chose deterministic counters and
bounded row storage rather than silently materializing full tables.

Tests include old Bonus 1/M1 regression cases, duplicate join keys, all
three join algorithms, hash and sort aggregation/distinct, empty grouping,
set operators, invalid columns/types, a LIMIT short-circuit, and a skew
fallback case. A separate measurement runner executes joins across three
sizes and four frame budgets and a sort larger than 20×B.

The full plan JSON schema published separately from M2 was not supplied;
`validate()` currently implements the shapes shown in M2.pdf. A global
frame tracker, more precise sort comparison counting, and textbook-cost
optimization of the staged BNL remain valuable improvements.

## Sources informing decisions

- Ramakrishnan and Gehrke, *Database Management Systems*, chapters 12–14:
  motivated the external merge stages and comparison against the textbook
  block nested loop I/O model.
- Graefe, *Volcano—An Extensible and Parallel Query Evaluation System*,
  IEEE TKDE, 1994: motivated the pull iterator lifecycle and bounded,
  operator-local resources.
- Shapiro, *Join Processing in Database Systems with Large Main Memories*,
  ACM TODS, 1986: motivated Grace hash partitioning with a robust overflow
  fallback rather than an unlimited in-memory hash table.

## Submission regression audit

Final additional checks include grouping followed by sorting on AVG results,
multiple frame budgets for duplicate-key joins, repeatable sort counters,
empty inputs for every join, set operations with duplicates, and early LIMIT
cleanup. The combined local suite passes 101 tests. This verifies tested
behaviour, not every possible global-frame or plan-schema scenario.
